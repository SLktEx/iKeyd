# Behavior DSL design

This document defines the direction for first-class, user-definable key behaviors in `.ikeyd`.

The central idea is simple:

- QMK-style helpers such as `LT()` and `MT()` should be easy to use.
- Those helpers should not be opaque compiler/runtime special cases.
- Users should be able to configure, extend, or replace their behavior with state-dependent logic.

The implementation issue is #99.

## Design goals

The DSL should support five levels of use without forcing advanced complexity on simple keymaps.

### 1. Plain mapping

```ikeyd
Q = "a"
```

### 2. Standard behavior

```ikeyd
POS[3,1] = LT(NUM, Z)
POS[3,2] = MT(Ctrl, X)
```

### 3. Per-instance configuration

```ikeyd
POS[3,1] = LT(NUM, Z) {
    tapping_term = 170ms
    permissive_hold = true
}
```

### 4. Reuse and selective override

```ikeyd
behavior KW_LT(layer, tap_key) extends LT(layer, tap_key) {
    on_interrupt(other) {
        if other == POS[2,1] {
            keep_tap()
        } else {
            resolve_hold()
        }
    }
}
```

### 5. Fully custom behavior

```ikeyd
behavior SMART_THUMB(tap_key, layer_name) {
    var interrupted: bool = false

    on_press {
        timer.start()
    }

    on_interrupt(other) {
        interrupted = true
    }

    on_hold {
        if state.vim_mode {
            layer.on(VIM)
        } else if state.symbol_mode {
            modifier.down(Ctrl)
        } else {
            layer.on(layer_name)
        }
    }

    on_tap {
        send tap_key
    }

    on_release {
        layer.off(layer_name)
        modifier.up(Ctrl)
    }
}
```

The exact surface syntax may evolve. The semantic model below is the important contract.

## Core semantic model

A behavior is not a keycode. It is an event-driven state machine attached to a key position.

A behavior consists of:

- parameters
- immutable configuration/options
- per-instance local state
- event handlers
- primitive actions

A behavior instance is created by binding a behavior definition to concrete arguments on a key.

```ikeyd
POS[3,1] = SMART_THUMB(Z, NUM)
```

The same definition may be instantiated many times with different options.

## Behavior events

The initial event set should be intentionally small and sufficient to express tap/hold semantics.

```text
on_press
on_release
on_tap
on_hold
on_interrupt(key)
on_timeout(timer)
```

`on_tap` and `on_hold` are semantic resolution events. They may be generated by a reusable tap/hold resolver rather than implemented independently by each behavior.

Future events may include observed key down/up events and multi-tap sequence events if they cannot be expressed cleanly through composition.

## Primitive actions

The runtime should understand generic primitive actions rather than hard-coded `LT`, `MT`, `OSM`, etc.

Initial primitives should include:

```text
send key/value
modifier.down(mod)
modifier.up(mod)
layer.on(layer)
layer.off(layer)
layer.toggle(layer)
state assignment
timer.start(...)
timer.cancel(...)
resolve_tap()
resolve_hold()
keep_tap()
```

The exact names may change, but standard behaviors and user-defined behaviors must ultimately execute through the same primitive action layer.

## State

Two categories of state are required.

### Profile state

Declared once and shared intentionally across behavior instances.

```ikeyd
state {
    vim_mode: bool = false
    symbol_mode: bool = false
    counter: int = 0
    last_key: key? = null
}
```

### Behavior-local state

Private to one active behavior instance.

```ikeyd
behavior EXAMPLE(key) {
    var interrupted: bool = false
    var tap_count: int = 0
}
```

State should be typed and validated at compile time where practical.

## Context reads

The first implementation should expose deterministic keyboard-runtime state such as:

- pressed keys
- active iKeyd layers
- active modifiers
- behavior-local variables
- profile state
- elapsed time / named timers
- interruption state
- current/previous key when available

Application/window/process state should be introduced later through an explicit capability boundary instead of being implicitly available to all behaviors.

## Standard behavior library

The following should be implemented as library behaviors on top of the same generic runtime model:

- `LT(layer, key)`
- `MT(mod, key)`
- `MO(layer)`
- `TG(layer)`
- `TO(layer)`
- `OSL(layer)`
- `OSM(mod)`
- multi-tap / tap-dance behavior

The implementation may use internal reusable primitives such as a tap/hold resolver, but the runtime should not contain independent top-level execution branches for every library helper.

## LT semantics

A default `LT(layer, tap_key)` needs a reusable tap/hold policy with configurable options.

At minimum, design for:

```text
tapping_term
permissive_hold
hold_on_other_key_press
retro_tapping
quick_tap_term
```

These names intentionally resemble established keyboard-firmware concepts, but exact compatibility is not required.

A behavior instance may override these values without redefining `LT`.

```ikeyd
POS[3,1] = LT(NUM, Z) {
    tapping_term = 170ms
    hold_on_other_key_press = true
}
```

## Reuse and override

Advanced layouts often need "normal LT except for one rule".

The language therefore needs behavior composition or inheritance.

Conceptual example:

```ikeyd
behavior CUSTOM_LT(layer, key) extends LT(layer, key) {
    on_hold {
        if state.vim_mode {
            layer.on(VIM)
        } else {
            super
        }
    }
}
```

The implementation does not have to use object-oriented inheritance internally. Macro expansion, composition, or handler delegation are acceptable if they preserve these semantics:

- reuse an existing behavior definition
- override only selected options or handlers
- invoke the inherited/default handling when desired
- avoid copying the entire standard implementation

## Ownership and cleanup

A behavior that presses a modifier or activates a layer owns that activation unless explicitly transferred/shared.

The runtime must guarantee cleanup when:

- the key is released
- the behavior is cancelled
- the input device resets
- the profile reloads
- the runtime exits unexpectedly through a handled failure path

This is especially important for custom behaviors; a user error must not leave Ctrl/Shift/layers logically stuck.

The IR should therefore track owned resources explicitly rather than relying only on arbitrary matching `down`/`up` instructions.

## Determinism and safety

`.ikeyd` behavior code is not a general-purpose scripting language.

Do not allow constructs that can block the keyboard event path indefinitely.

Initial restrictions:

- no unbounded loops
- no recursion
- no blocking I/O
- no process/network/filesystem access from a key event
- bounded timers
- bounded local storage
- typed operations
- compile-time validation where practical

This allows custom logic while keeping input latency and failure behavior predictable.

## Compilation pipeline

`.ikeyd` remains an authoring language. Runtime code should not parse behavior source text.

```text
.ikeyd source
    -> parser
    -> typed Behavior AST
    -> validation / lowering
    -> Behavior IR / state machine
    -> generated/static profile representation
    -> runtime executor
```

This separation is important for the existing static-compilation direction and for a possible future Rust runtime.

## Suggested IR concepts

The exact representation is implementation-defined, but it should contain concepts equivalent to:

```text
BehaviorDefinition
BehaviorParameter
BehaviorOption
BehaviorInstance
BehaviorEvent
BehaviorStateSlot
Condition
PrimitiveAction
TimerDefinition
ResourceOwnership
```

A keymap mapping should ultimately point to either a simple action or a behavior instance rather than directly to a string-only output.

## Compatibility

Existing mappings must remain valid throughout migration.

```ikeyd
Q = "a"
combo Q + W = "fa"
```

The compiler may lower legacy/simple values into a built-in `Send` action internally.

The current JSON/runtime path may coexist with the new representation during staged migration.

## First implementation slice

The first useful vertical slice should deliberately be small:

1. generic Action / Behavior IR
2. behavior invocation syntax in `.ikeyd`
3. per-key runtime behavior instance
4. timer + interruption handling
5. generic tap/hold resolver
6. standard `LT()` implemented on that resolver
7. per-instance `LT` options
8. deterministic tests for tap, timeout-hold, interruption-hold, release and cancellation

Only after that slice is stable should user-defined behavior bodies and inheritance/composition be added.

This sequence proves the generic runtime with a real QMK-style behavior without prematurely implementing a full language.

## Acceptance examples

### Normal LT

```ikeyd
POS[3,1] = LT(NUM, Z)
```

Tap emits `Z`; hold activates `NUM`; release returns to the previous layer state.

### Different LT policy per key

```ikeyd
POS[3,1] = LT(NUM, Z) { tapping_term = 150ms }
POS[3,2] = LT(SYMBOL, X) { tapping_term = 220ms }
```

Both use the same standard behavior implementation with independent configuration.

### State-dependent custom hold

```ikeyd
behavior MODE_LT(layer, key) extends LT(layer, key) {
    on_hold {
        if state.vim_mode {
            layer.on(VIM)
        } else {
            super
        }
    }
}
```

This must not require a special runtime code path for `MODE_LT`.

## Non-goals

The first Behavior DSL implementation is not intended to provide:

- QMK C source compatibility
- arbitrary C#/Rust/Python execution
- unrestricted operating-system automation inside event handlers
- an unbounded general-purpose VM

Those capabilities, where desirable, belong behind separate explicit action/capability APIs rather than inside the latency-sensitive behavior core.
